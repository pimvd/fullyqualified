# 11. One kind of asset

Status: proposed. Builds on ADR 0007 and ADR 0008. Settles issue #9.

- **Decision: flatten.** An asset is a monitored name, optionally with a port (`host` or `host:port`). `Asset.Kind` and the enum `AssetKind` are removed. `CloudResource` goes with it; it is never created and no check runs on it. Variant A (keep `Domain` and `Endpoint`, only drop `CloudResource`) was rejected: its kind is a guess from the name (a colon means endpoint), so `www.example.com` is already a "domain" and gets mail warnings it cannot act on, and it keeps two limits, two counters and a filter for a difference the user did not choose. Flattening removes all of that and the only thing it costs is the rules below.
- **Each check decides for itself, from the name and from DNS, with no setting, flag or public suffix list.** A check that has nothing to say about a name reports nothing: no warning, no failure.
  - `TlsCheck` applies to every asset, as it does now for everything but `CloudResource`.
  - `DnsCheck` has three parts. The per-name part (CNAME, dangling CNAME, A, AAAA, MX) and the mail part (SPF, DMARC, DKIM) run on every asset. The zone part (NS, CAA, DNSSEC, resolver comparison) runs only when the name has NS records, which only a zone apex has, so DNS itself tells `example.com` from `www.example.com`. `NoCaa` and `NoNs` are raised only inside the zone part. The mail rules are in the next section.
  - `CtLogCheck` (manual, "Find subdomains") applies to every asset that has no port and was not itself discovered. `Asset.Discovered` already exists and stops discovery from chaining.
  - The DKIM selector form is shown on every asset that was not discovered.
- **Mail rules, on every asset.** Best practice, checked per name, with no setting and no public suffix list.
  - **Sends mail** is decided from two facts: the name has an MX record other than the null MX (`0 .`), or it has an SPF record that is not just `v=spf1 -all` (compared case-insensitively, ignoring spacing). Anything else is a name that sends no mail.
  - **SPF** is read from the TXT records of the exact name, because SPF is not inherited.
  - **DMARC** is inherited, so the check asks for `_dmarc.<name>`, and if there is no record walks up one label at a time (`_dmarc.example.com` after `_dmarc.www.example.com`) until a record is found, and stops when one label is left. A record found above the name counts as coverage; the value shows where it came from. The policy that applies to the name is `sp` when the record belongs to a parent and has an `sp` tag, otherwise `p`.
  - **A name that sends no mail** should have SPF `v=spf1 -all` (`NoSpf` if there is no SPF record), a null MX (`NoNullMx` if it has no MX at all; a name that already has the null MX is fine), and covering DMARC with policy reject (`NoDmarc` if none; `DmarcNone` or `DmarcQuarantine` if weaker).
  - **A name that sends mail** needs an SPF record and covering DMARC (`NoSpf`, `NoDmarc`), and reject is the goal: `DmarcNone` and `DmarcQuarantine` are warnings, not errors. `~all` is accepted on a sender and is never flagged, so is `-all`. SPF content beyond presence (`+all`, include limits) is not judged here.
  - **An apex** (the name has NS records) must have a DMARC record at the name itself or above it with p=reject and either no `sp` or `sp=reject`; `DmarcSubdomainNotReject` is raised when `sp` is present and is not reject.
  - All of these are warnings. Only `DanglingCname` stays critical. The DKIM selector probe (the seven common selectors) runs only on names that send mail; selectors the user configured are always checked. Existing `DmarcNone` text is kept; the other new keys get English and Dutch fix texts in `Remedies`.
- **Cost.** The one loss of the earlier draft, that a name without MX gets no SPF or DMARC warning, is gone: every name is judged. The new costs are these. Every asset now needs one MX query, one TXT query for SPF and one `_dmarc` query per label walked (a host like `a.b.example.com` takes up to three when nothing is found, one when the record is at the name), plus the seven DKIM selector queries on names that send mail; before, only domains paid for these. That is roughly three to six more queries per name against 10 to 20 for an apex, run in the same sequence as now, so a scan of one asset takes tens of milliseconds longer and scans do not get meaningfully slower; scans run in the background on the plan interval, so nothing waits for them. The label walk has no public suffix list, so it may ask `_dmarc.co.uk`, which is harmless and finds nothing. The visible cost is more warnings: a tenant with many hosts that send no mail now sees `NoSpf` and `NoNullMx` on each of them, and `NoDmarc` only where no parent record covers them. That is the intended best practice and is not hidden. A name is treated as a sender when it has an SPF record other than `-all` even if it never sends; it then gets the softer rules and no `NoNullMx`. `CtLogCheck` on a name that is not a domain finds little and is harmless.
- **One limit: `MaxAssets`.** It replaces `MaxDomains` and `MaxEndpoints` on tiers, and `OverrideMaxDomains` and `OverrideMaxEndpoints` on tenants, with the same rules as before (null is unlimited on a tier, blank follows the tier on a tenant, -1 lifts it). Usage is the number of assets. It is enforced where assets are added, on the dashboard and during certificate discovery; the public check stores nothing and does not count.
- **Plan values, approved by the product owner.** `docs/PLAN.md` prices by number of domains and ADR 0007 has two limits. After this ADR a discovered subdomain and a manually added host use the same allowance as a domain. The starting values are Free 5, Starter 25, Business 100, Custom unlimited. They are lower than the sums of the old limits, so some tenants will be over them; that is settled as follows. **Nothing is deleted, paused or disabled.** An asset the tenant already has keeps being scanned and reported. `Blocks()` already refuses an add when usage is at or above the limit (`usage >= limit`), so a tenant with 7 assets on a limit of 5 simply cannot add new ones, on the dashboard or in certificate discovery, until it is back under; the screens show "7 of 5" with the existing limit message. No grace period and no notice are built; the owner can tell affected tenants in person. **Tenant overrides** keep the rule that makes the least change: the override is carried over as the sum of the two effective old values (override, otherwise old tier) when either was set, -1 if either was -1, blank if neither was set. Blank follows the new tier. An override is a deliberate grant by the platform owner, so it must not shrink, and one SQL rule per column is enough; the sum may be generous, and the owner can lower overrides in the existing tenant screen afterwards. The deploy note lists tenants whose override is set so the owner can review them. The table in `docs/PLAN.md`, the README and the marketing site are updated with the issue that changes the limits.
- **Reports and screens.** The report's domain-controls table lists the assets whose latest DNS result has zone values (so apexes, as DNS says), and its asset count is simply the number of assets. The dashboard drops the Kind column and the domain/endpoint filter (the existing source filter stays) and shows one count against one limit; `/limits`, organization, tenant list, plan summary and settings test show one asset line. `TenantStats` and the e-mail test, which picked `Kind == Domain`, use the non-discovered assets without a port.
- **Migration.** One EF migration, no data conversion: add `tiers.MaxAssets` and `tenants.OverrideMaxAssets`; set the seeded tiers by name to 5, 25, 100 and null (Custom), and any other tier row to the sum of its old limits (null if either was null); fill tenant overrides as described above, computed in SQL from the old columns before they are dropped; drop the old limit columns and `assets.Kind`; update the tier seed and code defaults to the new values. No asset rows are touched, so tenants over the new limit keep every asset. Deploy by stopping every container, migrating and starting the new version, because the old code reads `Kind`; with the worker container of ADR 0010 both services stop together. Rollback is the previous database backup; `Down` exists for development and is lossy (it recreates `Kind` as Endpoint for names with a port or a discovered flag and Domain otherwise, and sets both old limits to `MaxAssets`). A test builds a database at the previous migration with assets of every kind, tiers and overrides (unlimited, blank, set), including a tenant with more assets than the new tier allows, migrates it and checks the numbers: seeded tier values, override carry-over, no asset removed, and adds refused for the over-limit tenant. The first scan after the change adds `spf`, `dmarc`, `mx` and the DMARC source to every asset that lacked them, so each asset shows one change entry for the new keys and new warnings may appear; that is accepted.
- **Not included:** per-asset flags, the public suffix list, per-asset intervals (ADR 0008), and cloud resources, which return as their own ADR with a connector (phase 3) if they come back at all.
