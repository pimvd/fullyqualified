# 11. One kind of asset

Status: proposed. Builds on ADR 0007 and ADR 0008. Settles issue #9.

- **Decision: flatten.** An asset is a monitored name, optionally with a port (`host` or `host:port`). `Asset.Kind` and the enum `AssetKind` are removed. `CloudResource` goes with it; it is never created and no check runs on it. Variant A (keep `Domain` and `Endpoint`, only drop `CloudResource`) was rejected: its kind is a guess from the name (a colon means endpoint), so `www.example.com` is already a "domain" and gets mail warnings it cannot act on, and it keeps two limits, two counters and a filter for a difference the user did not choose. Flattening removes all of that and the only thing it costs is the three rules below.
- **Each check decides for itself, from the name and from DNS, with no setting, flag or public suffix list.** A check that has nothing to say about a name reports nothing: no warning, no failure.
  - `TlsCheck` applies to every asset, as it does now for everything but `CloudResource`.
  - `DnsCheck` always does the per-name part (CNAME, dangling CNAME, A and AAAA). The mail part (SPF, DMARC, DKIM selectors, MX) runs only when the name has an MX record. The zone part (NS, CAA, DNSSEC, resolver comparison) runs only when the name has NS records, which only a zone apex has, so DNS itself tells `example.com` from `www.example.com`. `NoSpf`, `NoDmarc`, `NoCaa` and `NoNs` are raised only inside those parts.
  - `CtLogCheck` (manual, "Find subdomains") applies to every asset that has no port and was not itself discovered. `Asset.Discovered` already exists and stops discovery from chaining.
  - The DKIM selector form is shown on every asset that was not discovered.
- **Cost of a wrong guess.** A domain that sends no mail and has no MX is no longer told it lacks SPF and DMARC, although such a domain can be spoofed; this is the one real loss, and a later ADR can add "or has an SPF record" if it matters. A host that has an MX but sits below its zone gets a `NoDmarc` warning because the policy is inherited from the apex. That is rare and accepted. A name searched in the certificate log that is not a domain finds little and is harmless. Scans do not get slower: the extra queries are skipped when the name has no MX or NS.
- **One limit: `MaxAssets`.** It replaces `MaxDomains` and `MaxEndpoints` on tiers, and `OverrideMaxDomains` and `OverrideMaxEndpoints` on tenants, with the same rules as before (null is unlimited on a tier, blank follows the tier on a tenant, -1 lifts it). Usage is the number of assets. It is enforced where assets are added, on the dashboard and during certificate discovery; the public check stores nothing and does not count.
- **This changes what the plans offer and needs the product owner's approval.** `docs/PLAN.md` prices by number of domains and ADR 0007 has two limits. After this ADR a discovered subdomain and a manually added host use the same allowance as a domain. Proposed starting values, so that no tenant loses room: Free 13, Starter 125, Business 600 (the sum of today's two limits), Custom unlimited. The owner may choose rounder numbers or a different public unit before the migration ships; the table in `docs/PLAN.md`, the README and the marketing site are updated with the issue that changes the limits. Tenant overrides become the sum of the two effective values (override, otherwise tier) when either is set, and -1 if either was unlimited, so nobody falls below what they have.
- **Reports and screens.** The report's domain-controls table lists the assets whose latest DNS result has zone values (so apexes, as DNS says), and its asset count is simply the number of assets. The dashboard drops the Kind column and the domain/endpoint filter (the existing source filter stays) and shows one count against one limit; `/limits`, organization, tenant list, plan summary and settings test show one asset line. `TenantStats` and the e-mail test, which picked `Kind == Domain`, use the non-discovered assets without a port.
- **Migration.** One EF migration, no data conversion: add `tiers.MaxAssets` and `tenants.OverrideMaxAssets`, fill them from the old columns in SQL as described above, drop the old limit columns and `assets.Kind`, and update the tier seed. Deploy by stopping every container, migrating and starting the new version, because the old code reads `Kind`; with the worker container of ADR 0010 both services stop together. Rollback is the previous database backup; `Down` exists for development and is lossy (it recreates `Kind` as Endpoint for names with a port or a discovered flag and Domain otherwise, and sets both old limits to `MaxAssets`). A test builds a database at the previous migration with assets of every kind, tiers and overrides (unlimited, blank, set), migrates it and checks the numbers. The first scan after the change drops mail keys for names without MX, so those assets show one change entry for the missing keys; that is accepted.
- **Not included:** per-asset flags, the public suffix list, per-asset intervals (ADR 0008), and cloud resources, which return as their own ADR with a connector (phase 3) if they come back at all.
