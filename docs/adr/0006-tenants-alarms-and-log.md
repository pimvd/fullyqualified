# 6. Tenants, alarms and the log

Status: proposed. Builds on ADR 0003 and 0004.

- **Tenants:** every account belongs to one tenant, and every tenant-owned table carries its id. The first tenant ever created, by the first account in `/setup`, is the **management tenant**; a unique index allows exactly one. Tenants are created by management admins, who invite each tenant's first admin. A self-hosted install for one company has one tenant.
- **Isolation fails closed:** the database context filters every tenant-owned table by the tenant in the session. A request that has no tenant, and is not background work, sees nothing. New rows take the current tenant, and a row with no tenant or for another tenant is refused when saved. Code that must cross tenants (sign-in, invitations, platform screens) says so with `AcrossTenants<T>()`; background jobs run with an explicit all-tenants scope, and each row they create copies the tenant of the asset it belongs to. The management role grants views and invitations across tenants, not a way around the filter.
- **Session:** the cookie carries the tenant and whether it is the management tenant, and is re-checked against the database like the role (ADR 0004). One account per e-mail address across tenants keeps SSO matching unambiguous.
- **Recovery:** a lost passkey is replaced through a single-use link (24 hours) that an admin issues for a user in their tenant, or a management admin for anyone. Using it registers a new passkey and removes all old ones. If nobody who could issue a link can sign in, the operator runs `recover <e-mail or name>` on the server, which needs host access and prints the link.
- **Alarms** are configured per tenant in the database: Slack and webhook addresses (encrypted with Data Protection), e-mail recipients, the lowest status that alarms, and whether recoveries and drift are reported. Webhook hosts pass the same private-address guard as scans, so a tenant cannot aim the server at the network it runs in. A tenant without settings uses the server-wide `Alerts:*` configuration, which keeps single-tenant installs unchanged. SMTP stays a server setting. Every delivery attempt is stored.
- **Log and charts:** the log screen reads check results (already kept in full), changes and alarm deliveries. Charts are server-rendered SVG with no script, follow the house mark rules, use the fixed status palette with an icon and a label for every status, and come with a table view. Results are not pruned yet; a retention period is open.
- **Users and tenants screens** show registered and last sign-in time (`LastLoginAt`, set at sign-in), and per tenant users, assets, certificates, certificates expiring within 30 days, assets with problems, last scan and changes in seven days.
- **Migration:** data from before tenants belongs to a management tenant created by the migration when there is anything to adopt; a fresh install gets its tenant from `/setup`.
- **Not included:** deleting or suspending a tenant, per-tenant scan limits and quotas (the plan's plans), a configurable certificate-expiry threshold per tenant, and result retention.
