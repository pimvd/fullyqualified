# 10. Scans in a separate worker container

Status: proposed. Builds on ADR 0002 and ADR 0008. Settles issue #3.

- **One image, one project, a role setting.** The worker is the same image and the same `Program.cs`, started with `Hosting__Role=worker`; there is no second project and no second Dockerfile. `Hosting:Role` is `all` (the default, today's behavior, so single-container installs and the test suite do not change), `web` (no `JobRunner`) or `worker` (only `JobRunner`). In the worker role the host registers the same services and configuration but maps no endpoints and listens on no port: it has no UI to serve, and no `Auth:*`, `Sso:*` or passkey code path to expose. Service registration moves into one shared method so both roles build the same container. `Scanning:Enabled=false` stays as a kill switch that turns the `JobRunner` off in any role. Migrations stay with the web role: the worker sets `Database:AutoMigrate=false` and needs no start order, because its loop already logs and retries every 3 seconds until the schema exists.
- **The scheduler is a Postgres advisory lock, not a flag.** Loop 0 of every process in the `all` and `worker` roles tries `pg_try_advisory_lock` on a fixed key, on one dedicated connection it keeps open. The holder runs `EnqueueDueAsync` (every minute) and retention (every 6 h); the others only claim jobs and try again on each tick. The lock disappears with the connection, so when the holder dies another replica takes over within a few seconds, and a flag could not do that: a mistyped flag would leave nobody scheduling, and a forgotten one would leave two. A new holder runs retention at once instead of waiting out the 6 hours, which is harmless because it is idempotent. The unique index on (asset, check type) stays as the safety net, so a lock that misbehaves costs wasted queries, not duplicate jobs.
- **One heartbeat, two sinks.** Every process that runs a `JobRunner` beats every 15 seconds, but only while every one of its loops has finished a tick in the last 60 seconds, so a stuck loop stops the beat. A beat (a) upserts a row in a new `worker_heartbeats` table (`WorkerId` generated at start, `StartedAt`, `BeatAt`, `IsScheduler`; rows older than a day are removed by the scheduler) and (b) touches `/tmp/fq-worker-alive`. Compose checks the file (`find /tmp/fq-worker-alive -mmin -2`), so the healthcheck needs no HTTP port, no `curl` and no database round trip. The settings test reads the table: a process is alive when `BeatAt` is under 60 seconds old. `worker_heartbeats` is platform state and carries no `tenant_id`, an exception to the rule in AGENTS.md of the same kind as `Tiers` and `DataProtectionKeys`.
- **The settings test asks for a heartbeat, not a flag.** `ScanItems` stops reading `Scanning:Enabled`. No live heartbeat is a failure ("scans are not running"), shown to tenant admins without server details; a live heartbeat with no `IsScheduler` row is a warning ("nothing schedules new checks"). The platform owner also gets the number of live processes and which one schedules. This works the same for `all`, so a single-container install passes without a worker.
- **What the worker needs.** `ConnectionStrings__Default`; `Scanning__Workers`, `Scanning__IntervalHours`, `Scanning__AllowPrivateAddresses`; `Dns__*`; `Alerts__*` (e-mail, Slack, webhook and Telegram fallbacks) and the `mail` network, because alarms are sent from the worker. It does not get `Sso__*`, `Auth__*` or `PublicScan__*`. `Scanning__ManualCooldownMinutes` stays on the web side. The web side still reports `Scanning:AllowPrivateAddresses` and `Alerts:Email:Host` in the settings test, so both services take them from one shared `x-scanning` environment block in `docker-compose.yml`, which keeps the report and the behavior from drifting apart.
- **Compose.** `app` runs with `Hosting__Role=web` and `worker` with `Hosting__Role=worker`; `worker` is scalable (`docker compose up --scale worker=2`) and has no published port. `docker-compose.yml` is the new default; self-hosters who want one container drop the `worker` service and leave `Hosting:Role` unset.
- **Not included:** a different queue, per-tenant or per-check worker pools, a separate worker project, an HTTP health endpoint on the worker, and the toolbox (#2), which may reuse the role setting later.
