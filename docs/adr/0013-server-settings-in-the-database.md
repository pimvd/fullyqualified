# 13. Server settings in the database

Status: proposed. Builds on ADR 0010 (the worker is a second container) and ADR 0007 (platform state without a tenant).

- **Decision.** The server settings that used to come only from environment variables and `appsettings.json` can be kept in a table `app_settings` (`Key`, `Value`, `IsSecret`, `UpdatedAt`, `UpdatedBy`) and are edited by the platform owner on the Settings page (`/settings`, `PUT /platform/settings`). The settings are listed in `AppSettingsCatalog`: key, group, kind (text, number, bool, secret, choice), the default the code uses, whether a change needs a restart, and for numbers a range. Only catalog keys count; a stray row is ignored, so the table can never override `ConnectionStrings:Default` or the role.
- **A configuration source, not a new settings API.** `DbConfigurationProvider` reads the table into `IConfiguration` and is added after every other source. All existing code that reads `cfg["Alerts:Email:Host"]` or `cfg.GetValue(...)` therefore sees database values unchanged, in the web container and in the worker, because both add it (`DbSettings.Add`). The database wins over the environment; deleting a row ("reset") brings the environment or the default back. A value that is empty on purpose is a row with an empty value, so it is different from "not set here".
- **Following changes.** The provider polls the table every 15 seconds and raises a reload when something changed, so a change reaches the web container and every worker replica within about that long. The process that saved it refreshes at once. No table yet (a fresh install before the migration), or no database, is not an error: the provider keeps what it has and tries again.
- **Left in the environment on purpose.** `ConnectionStrings:Default` (the database cannot hold its own address), `Hosting:Role` (chosen before the host exists, see ADR 0010) and `Database:AutoMigrate` (decides whether the table exists). They are not in the catalog.
- **Secrets.** SMTP password, webhooks, Telegram token, SSO client secret and the setup code are stored protected with the data protection keys that already live in the database (purpose `fq.settings`), so the worker can read them like the alert secrets of ADR 0007. They are decrypted once data protection is available after the host is built, so the non-secret values are there at startup and the secrets right after. The page never receives a secret: it shows only that one is set. An empty value is not a way to clear a secret; reset is.
- **Settings read once at startup** (SSO registration, the number of scan loops, the DNS clients, the private-address guard) are marked "restart needed" on the page. A change is saved at once and applies after the next restart; saying so is better than pretending it is live.
- **No `tenant_id`.** `app_settings` is platform state, an exception to the rule in AGENTS.md of the same kind as `Tiers`, `DataProtectionKeys` and `worker_heartbeats`. Only the platform owner can read or write it, and every change is logged with who made it.
- **Theme.** `Appearance:Theme` is the first setting that is about looks rather than operation: `default` changes nothing, `christmas` recolours the accent and the side menu through CSS variables on `<body data-theme>`. More themes are a catalog entry plus a CSS block.
- **Not included:** per-organization settings (those are the organization's own pages, e.g. alarms), a history of old values, import from the environment in one click, and editing the settings from the command line.
