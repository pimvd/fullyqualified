# 14. Azure Container Apps deployment with Terraform

Status: proposed.

- **Decision.** Infrastructure is Terraform only, with one exception: the storage account for the Terraform state is Bicep (`infra/bootstrap/state.bicep`), because Terraform cannot create its own state store. There are three roots, each with its own state in that storage account:
  - `infra/bootstrap.sh` (once): resource groups, the state storage, and the passwordless GitHub-to-Azure identities (OIDC).
  - `infra/shared`: the container registry (Basic) and the marketing site (Azure Static Web Apps, Free).
  - `infra/app`: one environment (`dev`, `prd`), in its own resource group: Container Apps (consumption), PostgreSQL Flexible Server (Burstable B1ms), Log Analytics with a daily cap, and a cost budget with e-mail alerts.
- **Separate images.** Three images, each with the role baked in, so nothing role-related is configured at deploy time: `fq-web` (`Dockerfile` target `web`), `fq-worker` (target `worker`) and `fq-postfix` (`deploy/postfix`). A plain `docker build .` still gives the role-from-environment image that docker-compose uses.
- **Build once.** A merge to `master` (`release` workflow) applies `infra/shared`, builds the three images tagged with the first 12 characters of the commit sha, pushes them to the shared registry and deploys that tag to dev.
- **Prd tags are hard-coded** in `infra/app/envs/prd.tfvars` (`web_image_tag`, `worker_image_tag`, `postfix_image_tag`). A prd release is a reviewed PR that changes them; the merge starts `deploy-prd`, which waits for approval on the `prd` GitHub environment. Prd is off until the repository variable `PRD_ENABLED` is `true`.
- **Mail.** The bundled Postfix runs as an internal container app (TCP 25, not reachable from outside the environment). Azure blocks outbound port 25, so it delivers through a smarthost on 587 (`smtp_relay_host`, with the user and password as GitHub secrets `SMTP_RELAY_USER` and `SMTP_RELAY_PASSWORD`). Its queue is not persisted across restarts.
- **DNS.** The zone `fq.vandijkcloud.nl` is in Azure DNS (`infra/shared`) and delegated once with NS records at the provider of `vandijkcloud.nl`; the name servers are printed in the `shared` workflow summary. Terraform creates the records: an alias A record for the marketing site on the zone apex, and per environment a CNAME plus `asuid` TXT (`infra/app`). Hosts: site `fq.vandijkcloud.nl`, dev `dev.fq.vandijkcloud.nl`, prd `app.fq.vandijkcloud.nl`. The workflows then bind the hostnames and managed certificates with the Azure CLI; until the delegation exists that step reports it and a re-run completes it.
- **Naming and tagging** follow the Azure Cloud Adoption Framework: `<type>-<workload>-<component>-<environment>-<region>` with the CAF abbreviations (`rg-fq-dev-weu`, `cae-fq-dev-weu`, `ca-fq-web-dev-weu`, `psql-fq-dev-weu-<suffix>`, `log-fq-dev-weu`, `id-fq-dev-weu`, `stapp-fq-site-weu`; `crfq<id>` and `stfq<id>` without hyphens). Every resource carries the tags Workload, Environment, Owner, Criticality, ManagedBy and Repository, and CostCenter when set (`cost_center`).
- **Why.** Fits the Visual Studio subscription credit (EUR 130 a month, spending limit on). No Application Gateway: Container Apps ingress gives HTTPS and managed certificates for free. The artefact that ran in dev is what prd runs.
- **Known trade-off.** Postgres is on its public endpoint (TLS required, Azure services allowed) to avoid the cost of a VNet and NAT gateway. Prd should move to VNet integration with a private endpoint.
- **Not included:** Terraform plan on PRs against real state, alerting beyond the budget mail.
