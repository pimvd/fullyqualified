# 13. A development environment on Scaleway Serverless Containers and Serverless SQL Database

Status: proposed. Builds on ADR 0009 and ADR 0010. Implements issue #30.

- **Decision.** A development environment runs as one Serverless Container (the existing image, all roles in one process) against a Serverless SQL Database, provisioned by Terraform and deployed by a manual GitHub Actions workflow. It is for development and demos. It is not the production design: production hosting stays open, and a regular Instance is still the better fit for it (fixed IP, open mail ports, a persistent disk, a database that guarantees advisory locks).
- **Why serverless for development.** Both resources scale to zero. An idle container costs nothing, and an idle database only bills its storage (about 1 GB, a few cents a month). A shared link for testing costs far less than an always-on machine.
- **What does not work there.** These are Scaleway's documented limits at the time of writing; some of the pages are more than a year old, so check them.
  - Serverless Containers accept only HTTP traffic, block outbound ports 25 and 465, have no static IP and an ephemeral disk. So the Postfix relay of ADR 0009 does not run, the toolbox's mail checks and any monitored endpoint on port 25 or 465 cannot be reached, and email goes out through an external SMTP server on port 587 (for example Scaleway Transactional Email). The DMARC test email, which needs a raw relay, is not available.
  - A Serverless SQL Database does not guarantee advisory locks and goes idle after 5 minutes without queries. The scheduler election of ADR 0010 uses a session advisory lock, so the container runs with `max_scale = 1`; the unique index on (asset, check type) stays the safety net. The job runner polls the database every 3 seconds, which keeps the database awake for as long as the container is awake, so the runner is off by default (`Scanning:Enabled=false`) and turned on from the workflow when scans are being tested. While it is off, queued checks (including "Check everything now") wait.
  - A container that scaled to zero starts slowly, and the first start also runs the migrations.
- **Shape.**
  - Terraform in `deploy/scaleway/terraform` creates a private registry, the container namespace and container (port 8080, `/health` for the startup and liveness probes), the serverless database, and an IAM application with a policy that allows only `ServerlessSQLDatabaseReadWrite` in the project, plus an API key whose secret is the database password. Secrets go into secret environment variables; nothing is committed.
  - The app is configured only through environment variables, with no code change: the connection string with `SSL Mode=Require`, `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` so the app trusts the proxy's `X-Forwarded-Proto` (without it passkeys and secure cookies break behind the TLS-terminating proxy), `Scanning:AllowPrivateAddresses=false` because the install is public, `Auth:SetupCode` so a stranger cannot claim an empty instance, and the SMTP settings. `Auth:Origin` and `Auth:RpId` default to the request host and can be pinned with a variable.
  - `.github/workflows/deploy-scaleway.yml` runs only on manual dispatch, in a protected GitHub environment, one run at a time. It creates the registry, builds and pushes the image tagged with the commit, applies Terraform and calls `/health` until it answers.
- **State and bootstrap.** Terraform state is kept in a private Object Storage bucket (S3-compatible backend). `deploy/scaleway/bootstrap.sh` creates the bucket and runs `terraform init` on a clean account; the bucket name is stored in an ignored local file and passed to the pipeline as a repository variable. The state contains the database password and the setup code, so the bucket stays private and is reachable only with the deploy key.
- **Teardown.** `deploy/scaleway/destroy.sh` asks for the bucket name, runs `terraform destroy`, and only when that succeeds empties and deletes the state bucket. A failed destroy keeps the state, so nothing is lost track of. The deploy API key itself belongs to whoever created it and is not removed.
- **Security.** The database endpoint is public and protected by TLS and a key limited to serverless databases in the project; the serverless products have no fixed address to allow-list. The container is public and the app does its own authentication.
- **Verified and not verified.** `terraform fmt` and `terraform validate` pass against the real provider (2.89), and an offline `terraform plan` with dummy credentials shows the seven expected resources. The scripts pass shellcheck and were run against stand-in `aws` and `terraform` commands to check the confirmation guard, the order of deletion and that a failed destroy keeps the bucket. The workflow passes actionlint. **Nothing has been run against a real Scaleway account**: the allowed CPU and memory combinations, the exact endpoint format of the database, the permission needed by the deploy key and the S3 calls against Object Storage are unconfirmed until the first real run.
- **Not included:** production hosting, Postfix, a custom domain and certificate, the batch-job design, monitoring and deploys on merge.
